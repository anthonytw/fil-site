Security and release keys

Every fil release is signed. Check these fingerprints against the copies in the repository before you trust one.

Release signing key

SSH, Ed25519. Signs the release tags and SHA256SUMS. In the repository: .github/release-signers.

SHA256:Q7KfBHSjAFRimlv46rQuCGxsQF0NHQgLTpBcekwvnp0

Since 2026-11-08. The retired key SHA256:sEx4DtGI9gdaVhgsYWwuIC0xwkYJ8BLIVhVktPHINvQ signed only the v0.1.0 tag.

Package signing key

OpenPGP, RSA 4096. Signs the .rpm packages and SHA256SUMS.asc. In the repository: .github/package-signing-key.asc.

9EF0 B189 34B7 0552 0F88 80A5 81C0 98D1 5D1A EC26

Since 2026-11-08. It replaced 8BD8 1C03 EC58 8C5E FD85 04C8 8C14 2300 4B6D DA01, which signed nothing released and is revoked (package-signing-key-revoked.asc).

Checking a download

Every file of a release is listed in SHA256SUMS, which is signed. Download it, SHA256SUMS.sig and the files you want from the 0.2.0 release, and release-signers from the repository's main branch, then:

ssh-keygen -Y verify -f release-signers -I release -n fil-release -s SHA256SUMS.sig < SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS      # shasum -a 256 -c on a Mac

With gpg, import the package signing key and run gpg --verify SHA256SUMS.asc SHA256SUMS. The .rpm files are signed with the package key, so rpm and dnf check them once the key is imported; the .deb files carry no signature of their own and are covered by SHA256SUMS. More in the install guide.

Security policy

Reporting a vulnerability

Please report security problems privately, through GitHub’s private vulnerability reporting: on github.com/anthonytw/fil, open the Security tab and choose Report a vulnerability. Don’t open a public issue or pull request for one.

Say what you found, the fil version (fil --version), the platforms involved, and how to reproduce it if you can. A report about what fil reveals about the people using it (its privacy rules are in DESIGN.md §11.1) is welcome too.

Supported versions

Only the latest release gets security fixes. A fix ships as a new release; older releases are not patched.

What happens next

  • You get an answer in the report, first an acknowledgment and then whether the problem is confirmed.
  • While a fix is made, the report stays private. You are kept up to date in it and can test the fix.
  • When the release with the fix is out, the advisory is published, crediting you unless you’d rather not be named.

This is a best effort, not a service-level promise. What fil defends against, and what it does not, is in security and privacy.
